# Implementation Plan: MD Library Interface

**Branch**: `002-md-library` | **Date**: 2026-05-10 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `specs/002-md-library/spec.md`

## Summary

Restructure the existing standalone `mojo-md` simulator into a proper Mojo package (`mojo_md/`) that any external Mojo codebase can import. The core change is moving all library modules into a `mojo_md/` subdirectory and adding an `__init__.mojo` that re-exports the full public API. A new `step() -> Float64` method on `Simulation` enables per-step state access. The standalone `main.mojo` CLI and all existing tests remain functional.

## Implementation Phases

### Phase A: Package scaffolding (prerequisite for everything)

1. Create `mojo_md/` directory
2. Move all `.mojo` files except `main.mojo` into `mojo_md/`
3. Fix all intra-package imports (e.g., `from atom import` → `from mojo_md.atom import` inside the package, or use relative imports if Mojo supports them)
4. Write `mojo_md/__init__.mojo` re-exporting the full public API surface (see contracts/library-api.md)
5. Update `main.mojo` to import from `mojo_md`
6. Update all `test/*.mojo` imports to use `from mojo_md import ...`
7. Verify CI command still works: `mojo run -I . test/test_atom.mojo`

### Phase B: Add step() method to Simulation

1. Refactor `Simulation.run()` to delegate to a new `step()` method
2. `step()` executes one full velocity-Verlet timestep and returns `Float64` (potential energy)
3. `run()` becomes a loop: `for _ in range(nsteps): var pe = self.step(); if self.step_count % print_interval == 0: print(...)`
   Note: the existing `var step: Int` field is renamed to `var step_count: Int` before adding the `step()` method to avoid a field/method name collision (Mojo does not allow both).
4. Verify numerical equivalence: same input → same PE/KE values from `run()` and manual `step()` loop

### Phase C: Usage example

2. Add `examples/custom_pair.mojo` demonstrating the custom `PairStyle` pattern

## Key Technical Notes

### Intra-package imports

Inside `mojo_md/`, modules that import each other (e.g., `simulation.mojo` imports `atom.mojo`) must use package-relative paths. Depending on Mojo 0.26.x behaviour, this is either:
- `from atom import Atoms` (if Mojo resolves siblings relative to the current file)
- `from mojo_md.atom import Atoms` (if absolute paths are required)

The CI runner uses `-I .` (repo root on path), so `from mojo_md.atom import` is always safe. Test this early in Phase A.

### step() return value and state

The `step()` method must leave `atoms.f` consistent with the *new* positions (i.e., forces are from the end-of-step force eval, same as after `run()`). Ghost forces are reverse-communicated before returning.

### sim_io.mojo Python dependency

`sim_io.mojo` uses Python interop for JSON parsing. It will remain in the package but is only needed for the `run_from_file()` path (used by `main.mojo -in`). Library consumers who don't use JSON config don't need to worry about Python availability.
